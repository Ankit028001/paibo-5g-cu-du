# PAIBO full stack on the simulated world v2 -- what exists, what was measured, what it does NOT show

**Everything below is measured on a SIMULATED world** (`paibo_bip/world2/`): users, mobility, radio, slices, sessions and bearer
requests are generated by a stated process (`world2/spec.py`). The six traffic classes' rate/packet-size parameters are the
project's real ns-3 values; the rest is a model. No result here is evidence about real users or a real network.

## The REAL dataset: `paibo_bip_dataset_merged.csv` (ns-3, 200 UEs x 30 s) -- what it supports (`python -m paibo_bip.real.evaluate_merged`)

This is the project's only real (ns-3) per-UE dataset. Everything above this line was built and evaluated on the simulated world
below, NOT on this file. What this file can and cannot support:

* **Structure:** one class per UE (80 mMTC, 30 Web, 30 Mobile, 24 VoD, 26 Live, 10 V2X); only throughput, cell throughput, SINR and
  tb_count vary in time; `drb_count` = 1 for every row (no information); no mobility, slice, time of day, bearer history, session
  sequence or multi-flow request. `packetSizeBytes` / `perUeCapBps` are configuration values that identify the class (leakage; not used).
  `onset_time_ms = registration_time_ms + bearer_setup_latency_ms` exactly.
* **Class from observed traffic:** 94 % (GBT) from the first second, **100 % from the first 2 s** (5-fold CV by UE, time-varying columns
  only; majority baseline 40 %). Easy because each class has a configured rate. It uses 1-2 s of traffic, i.e. it happens after a
  ~200 ms bearer setup would already be requested: it does not show prediction before a request.
* **Timing targets:** `onset_time_ms` is **not predictable** (best model MAE 28-31 ms vs 24 ms for the median; registration time
  dominates and is unpredictable). `bearer_setup_latency_ms`: class alone gives MAE 2.7 ms vs 7.1 (51 % within 5 %), +3 s of traffic 2.4 ms.
  The 0.5 ms / 99 % figure needs whole-run delay KPIs (correlation 0.985 with the target): an ex-post outcome, not usable before a bearer.
* **M1 on the real series (context 20 s, horizon 10 s, MAE kbit/s):** naive 3.91, mean-of-last-5 3.74, Chronos-Small zero-shot 4.32,
  fine-tuned on the simulated world 4.04, distilled student **19.95** (does not transfer). The real series are nearly constant
  (within-UE CV 0.10): **no forecaster beats the naive baseline**.
* **Not evaluable on this file at all:** next-bearer class from history, request timing from RRC events, GBR of the next flow, DRB
  count, multi-flow lists, slice constraints, mobility, time of day -- the data has none of those.

To make the paper's claims testable on REAL simulator data the ns-3 scenario must be extended (several sessions per UE with different
classes, mobility, slices, bearer-request timestamps); the simulated world below is a stand-in with the same structure.

## Measured results (held-out users, declared gates P(request) >= 0.5, P(first class) >= 0.7)

* App fingerprint (active app from flow characteristics): 81.3 %.
* Next bearer class (given a request): 68.7-69.0 % vs 65.3 % history-majority and 63.0 % last-class baselines; top-3 95 %.
* Request within 60 s on handover events: AUROC 0.716 (base rate 14 %), well calibrated (ECE 0.005).
* End to end: a BIV is prepared for **59.5 %** of connection events and for **0.2 %** of handover events. When prepared and a request
  follows: first 5QI correct **91.9 %**, exact ordered list 74.1 %, list covers all true 5QIs 89.8 %; reconciliation against the true Core
  flows: reuse-all **88.4 %**, reuse+delta 4.0 %, standard 7.6 %. Wasted speculation (prepared, no request) 0.07 % of events.
* Missing-input profile of the ns-3 testbed: 55.2 % / 91.5 % / 88.6 % -- almost unchanged. M2 on the distilled student's forecasts:
  indistinguishable from Small.

## Signal-presence sensitivity (does the pipeline use the other families when the signal exists?)

World v2 has a switch `coupling` ("activity begets activity": a UE already streaming opens related flows more often). Same pipeline,
coupling 0 / 1.5 / 3.0 (`bash`-free recipe: `PAIBO_COUPLING=... PAIBO_M1_DIR=... PAIBO_M2_DIR=...`, see `m2/sensitivity_report.py`,
`m2/group_ablation.py`):

| coupling | request AUROC on handovers | next-class accuracy (best baseline) | traffic block removed | block + last-request recency removed |
|---|---|---|---|---|
| 0 | 0.720 | 67.9 % (65.6) | +0.003 AUROC (nothing) | +0.002 |
| 1.5 | 0.800 | 61.6 % (59.1) | -0.007 AUROC, -0.34 pts | -0.013 AUROC, -0.70 pts |
| 3.0 | 0.853 | 62.3 % (58.4) | -0.007 AUROC, -0.12 pts | -0.022 AUROC, -0.75 pts |

Reading: when the mechanism exists the pipeline does exploit it, but the gain from the traffic-derived families (traffic history,
fingerprint, M1 forecast) is small (<= 2.2 AUROC points) because the bearer history already says the UE is active (a request a few
minutes ago). Drop-one ablation shows ~0 for each of them individually because they are redundant with each other and with the
history. The coupling is a modelling assumption introduced to test the pipeline, not a finding about real traffic.

## What the evaluation does NOT support (stated plainly)

* **The six feature families do not all contribute.** Drop-one ablation (next-class accuracy / request AUROC on handovers): bearer
  history -11.1 pts / -3.0; time of day -0.1 / -2.4; slice+registration -1.0 / 0; traffic history, app fingerprint, mobility, radio,
  cell context and **the M1 forecast: ~0 (|delta| < 0.2 pts)**. In this world new bearer requests do not depend on current traffic.
* **Handover events are essentially unpredictable** (a BIV is almost never prepared for them) and **time to request is not better than
  the median there** (15.0 s vs 15.1 s); the apparent time gain comes from the trivial connection events.
* **DRB count: no gain** over "always 1" (95.6 % vs 96.3 % among prepared); the model under-predicts multi-flow requests (1.01 vs 1.23
  flows).
* The class distribution, history dependence and slice constraints are **built into the generator**; a model finding them shows the
  pipeline works, not that real users behave this way.
* The live ns-3 Core only requests 5QI 9, the speculative bearer carries one non-GBR flow, and the gNB cannot supply radio/cell
  features: the live runs test mechanics and safe fallback, not prediction quality.
